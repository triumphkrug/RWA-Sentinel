# SPECA-lite Compliance Audit — RWA-Sentinel

**Audit date:** 2026-07-06 · **Method:** SPECA-lite (specification-driven auditing, arXiv 2026 pattern) · **Scope:** risk-scoring, cross-referencing, governance, oracle-slashing

## What this is

A lightweight, LLM-read structured comparison of the project's stated *specification* — README claims, docstrings, and naming — against what the running code actually does. This is **not** formal verification: no Z3/symbolic execution, no proof of absence of bugs. It answers one question per claim: *does the implementation actually do what the spec says it does, right now?* Re-run this manually after any significant change to scoring, governance, or slashing logic; it is cheap (a focused code read, no tooling) and catches the exact class of "looks right in the README, isn't wired up in code" gap that a careless demo would expose to a judge.

**Spec sources used:** `README.md` (`## 6-Factor Scoring`, `## DAO Governance`), inline docstrings/comments in `agent/src/validator/*.ts`, `agent/src/governance/dao.ts`, `agent/src/slashing/oracleSlashing.ts`, and the Rust contract source in `contracts/*/src/main.rs`.

## Findings

| # | Spec claim | Implementation reality | Severity | Status |
|---|---|---|---|---|
| F1 | README: Factor #2 "Document Integrity" (20%) — "Hash consistency and tamper-evidence of submitted document" | The actual 20%-weighted factor in `scoringFactors.ts` is `debtor_rating` (based on `debtorHistoryCount`) — an unrelated metric. A real `DocumentVerifier` class (`agent/src/validator/documentVerifier.ts`, 222 lines, hash/checksum/expiry checks) exists and is unit-tested (`tests/documentVerifier.test.ts`), but is **never imported or called** by the live scoring path (`server.ts`/`index.ts`/`localScorer.ts`). | High (README/code mismatch on a headline scoring factor) | Open |
| F2 | README: Factor #6 "Network Reputation" (10%) — "On-chain wallet history and prior attestation record" | The actual 10%-weighted factor is `detail_level` (invoice line-item count) — unrelated. A real `OracleManager` class (`agent/src/publisher/oracleManager.ts`) exists and is tested (`tests/oracleManager.test.ts`) but is **never imported** into the live pipeline. No wallet/reputation lookup feeds the composite score. | High | Open |
| F3 | README: "composite trust score... determines on-chain publication eligibility (threshold: 65/100, configurable)" | `LocalScorer` is configured with `trustThreshold: 60` in both `server.ts` and `index.ts` — a real, consistent 5-point discrepancy from the documented threshold. | Medium | Open |
| F4 | README/code docstring: "Cross-Reference Check... Corroboration against external data sources" / `CrossRefChecker`: "Checks invoices against multiple external data sources to detect inconsistencies or fraud signals" | `CrossRefChecker`'s `defaultSources()` (used everywhere it's instantiated — no alternate sources are ever passed in) only runs three **local** sanity checks: non-empty issuer/debtor strings, amount within a fixed range, due-date after issue-date. No network call, no external registry. Real external data adapters (GLEIF LEI lookup, OpenCorporates, CoinGecko — `agent/src/data/realDataAdapters.ts`) exist, are wired as standalone `/api/v1/data/*` endpoints, and work — but are **not** passed into `CrossRefChecker` or consulted anywhere in the scoring path. | High (the factor most directly implying "we verify against outside truth" does not) | Open |
| F5 | `AnomalyDetector` (`agent/src/validator/anomalyDetector.ts`, 289 lines — z-score/EWMA price-volume anomaly detection with staleness handling) is fully implemented and unit-tested (`tests/anomalyDetector.test.ts`). | Never imported by `server.ts`/`index.ts` — not part of the live scoring or oracle pipeline. A real capability that simply isn't switched on. | Medium (no false claim in README about this specifically, but it's presented in code as production-ready and isn't live) | Open |
| F6 | README "DAO Governance" section describes proposals with concrete on-chain effects (parameter changes, oracle add/remove, treasury spend). | `governance-dao`'s `execute_proposal` entry point (Rust) has **no differentiated action dispatch** — its own inline comment says "Perform the action based on action_type... not implemented in this example, just status update." Every proposal type has the identical on-chain effect (mark `STATUS_EXECUTED`); no scoring-weight update, no treasury transfer, no oracle set mutation actually happens on-chain regardless of `action_type`. | High for a judge testing "does a passed proposal actually do the thing" | Open — contract WASM redeploy is currently blocked (see A2/A3 notes: `ApiError::InvalidArgument` on install-transactions, root cause unresolved) |
| F7 | `oracle-slashing`'s `withdraw_stake` entry point is documented (by naming/route) as letting an oracle reclaim its own remaining stake. | The Rust implementation reduces the oracle's recorded `stake` value in storage but **never calls `system::transfer_from_purse_to_purse`** to actually move CSPR back to the caller. Bookkeeping decreases; no real funds move. Functionally broken (not a security hole — no unauthorized fund movement is possible either, see F9), but withdrawal doesn't withdraw. | Medium (functional bug, not exploitable) | Open — same redeploy blocker as F6 |
| F8 (positive) | README: 6 factors sum to 100% weight, 48h challenge period, asset-registry/attestation-store real testnet deployment. | Confirmed matching: factor weights in `scoringFactors.ts` sum to exactly 100 (25+20+15+15+10+15); challenge period is `172800` seconds = 48h in `oracle-slashing/src/main.rs`, matching the also-corrected `server.ts` config; both contracts verified live on testnet with matching entry points (see A2/A3 session notes). | — | Confirmed correct |
| F9 (positive, A1 finding) | No single key should be able to withdraw/escalate beyond its own capped stake or the DAO's collective process ("no-unilateral-withdraw"). | Audited all three contracts: `asset-registry` holds no funds and has no withdraw entrypoint; `governance-dao` holds no funds and has no treasury-withdraw entrypoint at all (only `veto_proposal`, installer-gated, which blocks rather than moves funds); `oracle-slashing`'s `withdraw_stake` is owner-gated and hard-capped at the caller's own recorded stake (`amount > stake` reverts) — no path for any single key to drain pooled/other-owner funds. | — | Confirmed no exploit |

## Priority for remediation (if time allows post-deadline)

1. **F4** (cross-reference doesn't cross-reference externally) — highest reputational risk if a judge reads `crossRef.ts` next to its own docstring. Fix: pass the real `realDataAdapters` LEI/price lookups into `CrossRefChecker` as actual `sources`.
2. **F1/F2** (README factor descriptions vs actual factor implementations) — either wire `DocumentVerifier`/`OracleManager` into `scoringFactors.ts`'s evaluators, or correct the README table to describe the two factors that are *actually* running (`debtor_rating`, `detail_level`).
3. **F3** (threshold 60 vs 65) — trivial one-line fix in either direction; needs a decision on which is correct.
4. **F6/F7** — both require a contract WASM redeploy, currently blocked by the unresolved install-transaction `ApiError::InvalidArgument` (see A2/A3 session notes); track as a known limitation until that's resolved.

## Explicitly out of scope for this pass

Formal contract verification (Z3/symbolic execution over the Rust/Wasm), fuzzing, and gas-cost/DoS analysis are not covered here — SPECA-lite is a structured "spec vs implementation" reading, not a security proof.
