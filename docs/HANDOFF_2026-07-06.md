## 4. Open blocker: WASM install/redeploy (full diagnosis in `docs/WASM_INSTALL_DIAGNOSIS.md`)

Two independent, **confirmed** root causes prevented redeploying `governance-dao`, `oracle-slashing`, `asset-registry`, `attestation-store`:

### 4.1 `CLType::Any` as entry-point return type — ROOT CAUSE CONFIRMED, FIX CONFIRMED WORKING
- Node instantly rejects install of any WASM with an entry point returning `CLType::Any`, regardless of size.
- Fixed in code (commit `5cf0e5c`): replaced with concrete tuple `CLType` in `asset-registry.get_asset` and `attestation-store.get_attestation`.
- Rebuilt (52.7KB) and redeployed to testnet: `ApiError::InvalidArgument` **disappeared**. Deploy then failed only on "Insufficient funds" because the deployer had drained its testnet CSPR after ~10 test attempts.
- **Javier funded the faucet at 22:12 UTC.** This fix should now let a full successful redeploy go through on the first real attempt — **do this first**, then run full regression (235 tests + CI) and confirm prod isn't affected, update prod config with the new on-chain contract hash if the redeploy changes it.
- Only applies to asset-registry/attestation-store (they use `CLType::Any`); governance-dao/oracle-slashing don't have this issue, they have issue #2 below.

### 4.2 casper-js-sdk misroutes install/upgrade txs into the wrong lane — UNRESOLVED, likely node/SDK bug
- governance-dao (~3KB over) and oracle-slashing (~460 bytes over) still exceed the 65,536-byte "lane 5" cap even after `[profile.release]` fix + aggressive `wasm-opt -Oz`.
- Chainspec says install/upgrade txs should get a 750KB lane (`install_upgrade_lane`), but `casper-js-sdk@5.0.12` through `5.0.16-beta2`'s `SessionBuilder().installOrUpgrade()` gets rejected identically to a plain call-lane tx whether serialized as TransactionV1 or legacy Deploy — confirmed via raw JSON payload inspection, `isInstallUpgrade: true` is set correctly, so this looks like a node/execution-engine-side lane-classification bug, not an SDK bug.
- Attempted and exhausted this session: SDK version bumps (up to 5.0.16-beta2), checked GitHub issues, checked `casper-client` Rust CLI (blocked: sandbox has no root, missing `libssl-dev`/`pkg-config`, so cargo can't build the OpenSSL-linked crate).
- **Not yet tried, worth 30-40 min before giving up** (Javier called this "very important"):
  a. Further binary shrink: `panic = "abort"` (partially done), strip debug/producers sections, more aggressive `wasm-opt` DCE passes — governance-dao is only ~3KB over, oracle-slashing only ~460B over, so this is the most promising path.
  b. Build `casper-client` with a vendored/rustls TLS feature flag instead of system OpenSSL, to sidestep the missing headers.
  c. Construct the raw JSON-RPC transaction manually, bypassing `casper-js-sdk`'s `SessionBuilder`, forcing explicit `install_upgrade_lane` category assignment.
  d. Try CSPR.cloud as the broadcasting RPC provider instead of the default node, in case lane routing differs by provider (already using CSPR.cloud for reads/prod, not yet tried for install broadcast).
- If none of (a)-(d) work in a focused session: **document as an honest known limitation** in `docs/WASM_INSTALL_DIAGNOSIS.md` (already drafted) and in the submission notes — this is defensible (root cause identified, reproduced on a minimal contract, workaround path documented) rather than a silent gap.
