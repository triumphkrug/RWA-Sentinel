## 2. All bugs found + fixes (chronological, don't re-litigate these — they're closed)

1. **Cargo profile bug**: per-package `[profile.release]` silently ignored by Cargo; must be at
   workspace root. Fixed — cut WASM sizes by ~50-60% (asset-registry 136KB→53KB, governance-dao
   136KB→68.4KB, oracle-slashing 147KB→65.6KB after `wasm-opt -Oz`).
2. **`CLType::Any` as an entry-point return type** — node instantly rejects install of any WASM
   with this, regardless of size. Fixed: replaced with concrete tuple `CLType` in
   `asset-registry.get_asset`/`attestation-store.get_attestation`. Confirmed working: after this
   fix, `asset-registry`/`attestation-store` deployed successfully (their **first-ever**
   successful install after the fix — they'd never been live before).
2.1. **`casper-contract 5.1.1`'s panic handler uses `#[no_mangle]` on a lang item** — breaks
   under newer nightly compilers (e.g. `nightly-2025-08-28`). Fixed in casper-node's in-repo
   copy, not yet republished to crates.io. Workaround: stay on `nightly-2025-02-01`/`-04`.
3. **Oracle-slashing purse-slashing bug** (A1 audit): source-level fix applied, compiled,
   committed — **not deployed** (blocked by §3 below).
4. **`dao_oracles` allow-list starts empty at install** — `batch_attest` requires caller to be a
   registered oracle; no bootstrap step existed. Fixed live: call `register_oracle`
   (installer-only) once before first real `batch_attest` batch. Documented in
   `KNOWN_LIMITATIONS.md`.
5. **CLValue-parsing bug specific to CSPR.cloud's response format** (differs from raw node RPC
   format) — fixed during B2 (GovernanceDAO full-cycle) work. Watch for this class of bug if
   adding new CSPR.cloud read paths.
6. **GLEIF adapter field-name mismatch** — fixed during B4 work.
7. **Fake/simulated BLS threshold signatures** — replaced with real BLS12-381 3-of-5 via
   `@noble/curves` (B3).
8. **kyc-gate contract** (S4): new contract modeled on official
   `casper-ecosystem/kyc-proxy-contract` reference, compiled, committed — **not deployed**
   (blocked by §3).

## 3. THE open blocker: WASM install/redeploy `ApiError::InvalidArgument [3]`

Full technical log across **9 investigation rounds**: `docs/WASM_INSTALL_DIAGNOSIS.md` (~630
lines) — read that file for full detail; this is the executive summary.

**Symptom**: any attempt to install/redeploy `governance-dao`, `oracle-slashing`, `kyc-gate`
(new, never-deployed) reverts with `ApiError::InvalidArgument [3]`. Confirmed via raw
`info_get_transaction` RPC against `https://node.testnet.casper.network/rpc`: execution effects
contain **only** balance-hold/release (fee), **zero** contract/package state effects — the
revert happens **before** `create_contract_package_at_hash`/`add_contract_version` ever runs.
Gas consumed is a small, **constant** value regardless of wasm content/size/format (2,847,550 for
legacy `Deploy`, ~3,063,235 for `TransactionV1` — different per format but identical *within* a
format across attempts with genuinely different wasm bytes) — strongly suggests rejection at a
fixed, generic, pre-execution validation point, not anything contract-specific.

`asset-registry`/`attestation-store` **do** install/redeploy successfully (their fix was
`CLType::Any`, see §2 item 2) — so the pipeline/toolchain/deploy scripts themselves work; this is
specific to `governance-dao`/`oracle-slashing`/`kyc-gate`.

### Hypotheses tested and RULED OUT (do not re-test these — confirmed dead ends)
- `CLType::Any` (governance-dao/oracle-slashing don't use it)
- WASM size / lane cap (`install_upgrade_lane` = 750,000B max, our binaries are ~90KB, well under)
- Legacy `Deploy` vs `TransactionV1` format (both fail identically)
- Named-key collision from prior successful install (renamed to `_v2`, still failed identically)
- Payment/pricing-mode fields (present and correctly formed, verified against raw payload)
- Permission-check path (`ApiError::NotAllowedToAddContractVersion` is a *different, distinct*
  error code — not what we see)
- `nightly-2025-08-28` toolchain swap (doesn't even compile, see §2.1)
- Bulk-memory/unsupported Wasm opcodes (our binary parses fine against the actual `casper-wasm
  1.0.0` crate casper-node depends on)
- `casper-types` 6.1.0 vs 7.0.0 version gap (real gap, but install-relevant source is identical
  between versions, see §1 table)
- Wasm memory/stack limits (`max_memory`=64 pages/4MB, `max_stack_height`=500 in chainspec; our
  binary declares 17 pages/~1.09MB — well under)
- `install_upgrade_lane` max-args-length (2048B cap; we pass empty/near-empty args)

### New fact found, not a fix but worth knowing
- Testnet chainspec caps the install/upgrade lane to **1 transaction per block, network-wide**
  (`install_upgrade_lane = [2, 750_000, 2048, 1_000_000_000_000, 1]` — last field is max tx count
  per block). Could cause delayed inclusion under hackathon-wide congestion, but would not cause
  an executed-and-reverted transaction — doesn't explain our symptom.

## 5. Practical gotchas for whoever continues this

- `scripts_deploy/` and `keys/` and `*.pem` are gitignored — **not** in the repo, live only in
  the local sandbox that created them. If starting a fresh session/sandbox, you must recreate the
  deploy script (`SessionBuilder().installOrUpgrade()` via `casper-js-sdk ^5.0.12`, or the legacy
  `Deploy`/`putDeploy` variant that was also built and tested) — both are described in full in
  `WASM_INSTALL_DIAGNOSIS.md`'s Update 4 section. The deployer secret key persists at
  `skills/projects/ae402_hackathon/keys/deployer_keys/triumphkrug_secret_key.pem` (shared skill
  location, survives across sandboxes) even though the project-local copy doesn't.
- Query `info_get_transaction` directly against `https://node.testnet.casper.network/rpc` (not
  just CSPR.cloud) to see full `execution_result.effects` — CSPR.cloud's own API doesn't surface
  this level of detail as easily.
- Use GitHub `search/code` API (`api.github.com/search/code?q=...`) against
  `casper-network/casper-node` for exact error-message provenance in the execution engine source
  — much faster than browsing the repo manually.
- crates.io API needs a `User-Agent` header set or requests silently return `{}`/error instead of
  the expected JSON (no error message, just missing key — easy to misdiagnose as "no data").
- Local WASM analysis: `uv run --with wasmtime python3 ...` works for quick prototyping, but
  wasmtime's own feature-flag/encoding for `call_indirect_overlong`-style extensions doesn't
  necessarily match casper-wasm's actual fork — don't trust wasmtime-based validation failures as
  evidence about casper-network behavior; build a tiny Rust harness against `casper-wasm` /
  `casper-wasmi` crates.io crates directly instead (fast: ~1 min compile, see Update 8 in
  `WASM_INSTALL_DIAGNOSIS.md` for the exact harness code, since deleted after use — small enough
  to recreate in under 5 minutes if needed again).
